# Gate 4 implementation specification

Gate 4 runs Java 21 platform threads in the same standalone executable as compiled, interpreted, and late-loaded code. Both engines use the same logical thread identities, monitors, class initialization protocol, and shared-memory operations. Acceptance covers cross-engine synchronization, waiter cancellation, safe publication, and concurrent Gate 3 plugin use. [Architecture](ARCHITECTURE.md#7-threads-monitors-and-the-java-memory-model) · [Gate 4 tests](GATE4-TESTING.md)

## Profile and build

Add `catty build --enable-threads` for profile `catty-jvm21-gate4` and image ABI `4`. It includes Gate 3 plugin admission, so combining `--enable-threads` with `--enable-plugins` also selects Gate 4. The existing flag alone selects Gate 3 and the default selects Gate 2. Preserve earlier profiles' method selection, bootstrap and opcode inventories, and rejection diagnostics. Fields bearing `ACC_VOLATILE` already pass through the single-threaded profiles. Gate 4 gives them multithreaded Java semantics.

Extend `rt.Profile`, `rt.Image`, and the build report with a threading flag, serialized as `threads`. Gate 4 advertises `threads: true`, `plugins: true`, existing Gate 3 limits, the capabilities `threads`, `monitors`, and `synchronized-memory`, and the Gate 3 capabilities. Its opcode inventory adds exactly `monitorenter` and `monitorexit`. The profile supplies canonical inventories for both image and report. Installation validates profile/ABI/feature flags before Java runs, and checks actual retained opcodes and synchronized flags against the declared profile even when a supplied image omits its inventory. Older image flag omissions decode as false. Keep the existing Java `Entry`, `Outcome`, and `Value` calling conventions.

Decode both monitor instructions as single-byte instructions in `internal/classfile/code.go` under Gate 4. Share the profile decision between application build, plugin decoding and verification, and image installation. The verifier consumes one operand matching the JVM `reference` verification type and produces no stack value. Preserve exceptional handler edges and original PCs. Reject illegal flag combinations, including synchronized instance constructors, synchronized abstract methods, and ordinary synchronized interface methods. Apply the version-specific JVMS rules for `<clinit>` and ignore its synchronization flag for execution. Reject unsupported native methods as before. Permit ordinary concrete synchronized class methods without changing their descriptors. Keep existing field-flag checks and reject a Gate 4 field that is both final and volatile. Gate 4 applies per-operation ownership checks to hand-authored monitor instructions. [JVM method and field flags](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.5) · [JVM verification rules](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.10.1.9)

Implement both opcodes in `rt/interpreter.go` and `internal/aot/emit.go`. Route them through `Thread.MonitorEnter` and `Thread.MonitorExit` with the existing throwable transfer path at the instruction PC. For a compiled method, use the same handler selection as other throwing helpers. Keep `--mode aot` strict for image methods and keep admitted plugin bodies interpreted.

The supported surface is the designated bootstrap subset, Java platform threads, and the existing classpath and plugin policies. Java-defined class loaders, virtual threads, thread groups, thread locals, executors, park/unpark, Java thread inspection, native methods, agents, and JDK synchronization utilities are outside this profile. Explicit VM exit, shutdown hooks, and application measurement belong to Gate 5.

Use the access, static, and final flags shown in the table. Both exception constructors, `()V` and `(Ljava/lang/String;)V`, use the existing throwable helpers.

## Logical threads and launcher

- Extend `rt.Thread` with its Java peer and lifecycle state. Thread construction creates the peer state once, with a stable positive runtime-local ID, optional `Runnable`, name, and daemon flag inherited from the constructing logical thread. A null runnable means an empty base `run`. A null explicit name throws `NullPointerException`. Default worker names use `Thread-<number>`. Main has a canonical peer named `main` and starts non-daemon. Thread state remains accessible from the peer after termination. Only live executions need registry roots.
- A single transition from new to started publishes identity, daemon status, and launcher accounting before scheduling the worker on a goroutine. A second `start` throws `IllegalThreadStateException`, even after termination. Run the selected virtual `run()V` with the peer as receiver on the new logical thread. The default `Thread.run` invokes the supplied task through the shared interface selector. A direct Java call to `run` uses the caller's logical thread and does not change lifecycle state. Use `Thread.Call` for all entries, including reflection and synchronous host callbacks, and give each logical thread exclusive ownership of its frames and locals. The Gate 4 launcher and `Thread.start` are the entry points for asynchronous Java execution.
- `isAlive` observes started through terminating execution, and a false observation after termination and successful terminating `join` receive the terminating thread's writes. A join on a new or terminated thread returns without waiting. For a live platform thread, use its peer monitor and a loop over liveness, including the wait protocol below. Termination publishes state and notifies all joiners while holding that monitor. A timed join preserves one deadline across wakeups and returns when the target terminates or the deadline expires. Join interruption throws from the joiner and clears its status. The target's execution is independent.
- `setDaemon` throws on a live thread. On a new or terminated thread it changes the stored flag. `interrupt` records a pending interrupt and wakes an interruptible blocker. Preserve the pending bit on new and terminated peers as in the OpenJDK reference implementation. `isInterrupted` observes without clearing and static `interrupted` tests and clears the current peer. Monitor entry and class initialization waits preserve interrupt status.
- Implement `sleep` as an interruptible timer that keeps all owned monitors. A pending interrupt causes even a zero-duration sleep to throw and clear status. Require nonnegative milliseconds and nanoseconds in `0..999999` for the two-argument forms of sleep, join, and wait. For wait and platform join, round a positive nanos remainder up to one millisecond with saturation. For sleep, sum the duration in nanoseconds and saturate at the signed 64-bit nanosecond ceiling. Use a monotonic clock and bounded timer segments for wait/join durations exceeding Go's duration range. Keep zero distinct from overflow. `yield` makes a scheduling hint and adds no Java synchronization edge. [Java 21 Thread API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Thread.html) · [Java 21 Thread source](https://github.com/openjdk/jdk21u/blob/master/src/java.base/share/classes/java/lang/Thread.java)
- At the launcher boundary, report uncaught Java exceptions with the terminating thread's Java name and its Java frames. Serialize each diagnostic as a unit. A worker's uncaught Java exception terminates that worker and leaves the main-derived status unchanged. After main returns or throws, wait for started non-daemon executions to finish, including any started before the live count reaches zero. Daemons may still be running at process exit. A normal main yields status `0`, an uncaught main throwable yields `1`, and image/host setup failure yields `2`. A Go panic remains an implementation fault. Keep the launcher's startup and argument behavior. [JVM termination](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.7) · [Architecture launcher contract](ARCHITECTURE.md#8-application-startup-fallback-and-exit)

## Monitors and wait sets

Keep optional monitor state on the Java object so its lifetime follows the object. The same object pointer denotes the same monitor in each engine, including arrays and class mirrors. Avoid a runtime map that roots every monitored object. Use a runtime mutex for short thread, monitor and wait-set bookkeeping transitions. A monitor has an owner `*Thread`, recursion depth, an entry wakeup mechanism, and a wait set. Ownership and all thread blocker/status changes use that mutex. A waiting goroutine releases the mutex before parking. Recheck predicates after waking. No fairness guarantee is required.

- Enter on an unowned monitor claims it at depth one. The owner may enter again. A contender parks until it can acquire the monitor, with its interrupt bit left alone. Exit by the owner decrements the depth, waking entry contenders at zero. Illegal exit throws `IllegalMonitorStateException` and leaves state unchanged. Null throws `NullPointerException` for both opcodes and for `Thread.holdsLock`. `holdsLock` checks current logical thread ownership.
- Implicit method locking belongs to `Thread.Call` after invocation resolution, receiver/access checks, and active-use initialization. Lock the receiver for an instance method or the selected declaration's canonical class mirror for a static method. Release exactly one acquisition on Java return or unwind before reporting the outcome to the caller. If hand-authored bytecode has already relinquished ownership, report `IllegalMonitorStateException` at the method boundary. An inner handler executes with its method's implicit monitor still held. Explicit block cleanup follows the class-file control flow and its exception table. Preserve original throwable identity across generated, interpreted, and reflective frames when monitor release succeeds. [JVM monitor instructions](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html#jvms-6.5.monitorexit)
- For wait, validate arguments and ownership before consuming interrupt status. With a pending interrupt, clear it and throw while retaining the current recursion depth. Otherwise under the bookkeeping mutex record the depth, insert a waiter, publish the thread's active blocker, and fully release the monitor. Untimed wait and timed wait with zero arguments park without a deadline. Positive timed wait can be removed by timeout. Always reacquire the same monitor to the full saved depth before returning or throwing.
- `notify` and `notifyAll` require ownership even when the wait set is empty. One notification claims one eligible waiter, and notify-all claims the current eligible set. The notifier retains ownership. Notification is not buffered for future waiters. Use one waiter state transition from pending to notified, timed out, or interrupted, under the same mutex as the interrupt bit. Only a winning transition removes the waiter and makes it runnable. If interruption wins, the waiter is ineligible for subsequent notification, and clears the bit as it throws after reacquiring. If notification or timeout wins, a later interrupt stays pending on normal return. Cancel or ignore timer callbacks for old wait records. Cover stale timers, interrupt during reacquisition, and absence of lost notifications when another waiter remains eligible. [JLS wait sets and interruption](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html#jls-17.2)

## Shared memory and runtime state

Use one runtime memory mutex for all accesses to published Java instance and static slots and array elements, including ordinary accesses. Both engines already use the helpers in `rt/thread.go` for the common paths. Put the synchronization at the slot access and preserve conversions, exceptions, access checks, and initialization ordering. A field or array element access is atomic at its Java value width, including reference, `long`, and `double` values. Volatile reads and writes share a total order across all objects and classes. A read-modify-write sequence remains multiple Java actions. A single ordered memory path also implements constructor and final-field publication conservatively. The runtime may produce a subset of JMM-permitted outcomes in racy programs. [JLS memory model and final fields](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html#jls-17.4) · [Go memory model](https://go.dev/ref/mem)

Audit all direct storage accesses outside those helpers. `rt/intrinsics.go` must snapshot reflection parameter types and arguments under the memory mutex and release it before resolving or invoking Java. `Plugins.register` takes one bounded snapshot of the byte array under that mutex and passes only the copy to admission. Host reads such as `StaticValue` and any array helpers used after publication must go through synchronized accessors. Direct initialization of private arrays and objects is allowed before publication. Array length, kind, and component metadata are fixed. Freeze immutable runtime payloads before publication or protect their remaining mutation, including throwable cause/message/frame data. Eliminate lazy, unsynchronized payload writes on shared values.

Use a distinct runtime metadata mutex for resolution and dispatch caches, loader publication and counters, initiation/constraint state, lazy arrays and mirrors, string and boxing interning, and any other shared mutable lookup state. Preserve canonical object identity under concurrent misses. Publish complete class and method metadata together, and keep it immutable after publication. Use a race-safe monotonic object identity source. Failed admissions can consume internal, unobservable object IDs. They cannot rewind the counter or consume a published loader ID. Use the same metadata access paths in legacy runtimes where possible.

Keep the memory, metadata, and thread/monitor mutexes out of Java execution, monitor waits, timer waits, class initialization waits, admission callbacks, and host I/O. Structure shared helpers as locked operations plus caller-owned wrappers so nesting does not reenter a Go mutex. Initialize or resolve before reading or writing a slot. Create a Java exception after releasing bookkeeping locks, using failure details captured under the lock. Use atomic or otherwise synchronized trace publication. A trace flush or diagnostic must never acquire a runtime state lock. Startup-only hooks and options are installed before workers can run. [Go memory model](https://go.dev/ref/mem)

## Class initialization

Give each defining class its own initialization guard, owning logical thread, and completion signal. A class literal uses the mirror and does not trigger initialization. Active use follows the existing common path for bytecode, reflection and class lookup.

1. Under the guard, an initialized class returns successfully and an erroneous class yields a new `NoClassDefFoundError`. Reentry by the owning `*Thread` succeeds with the current static values. Another thread copies the completion signal and waits outside the guard, then rechecks state. Its interrupt bit is untouched.
2. On the first use, publish the initializing state and owner. Outside the guard, assign `ConstantValue` fields in declaration order through the shared memory path, initialize required superclass and default-method interfaces in existing JVMS order, then invoke `<clinit>` through `Thread.Call`. The initialization guard is separate from the Java class mirror monitor.
3. Publish completion and wake all waiters on every Java outcome. The owner receives the original `Error` from the initializer, or an `ExceptionInInitializerError` that retains the original non-`Error` throwable as its cause. Failure in a required parent marks the child erroneous and propagates that failure. Use the same guard for success observation and completion publication to establish visibility of the initializer's writes. Never rerun an erroneous class. A cyclic dependency between threads can deadlock under JVM rules. [JVMS initialization](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.5)

## Concurrent plugin admission

Keep Gate 3 parent-first identity and archive rules. Snapshot the parent chain's published immutable definitions and the private input bytes, then run the bounded admission adapter outside shared runtime locks. The adapter validates a detached candidate using the Gate 4 profile. During commit, recheck the parent handle and current limits and validate candidate loading constraints against current state under the metadata mutex. Quota accounting, constraints, staging of array classes and canonical mirrors, and loader publication are one commit. A rejection discards candidate-only changes without undoing unrelated concurrent resolutions or admissions. Commit builds metadata without running Java code. Return a canonical loader mirror only after commit and trace publication. Previously published classes keep their identity and compiled receiver guards. Calling through a late plugin can initialize a class, allocate a monitor, or start a thread on either side of the existing ABI. [Gate 3 admission contract](GATE3.md)

## Trace contract

Keep existing JSON-lines fields for Java frames, plugin decisions, dispatch and initialization. Preserve process identity, per-thread frame order, loader IDs, original PCs, and stable throwable IDs. Make trace writes and close safe when daemon activity overlaps process exit. Emit each event atomically. Record transitions in order as part of state publication and flush to the file outside runtime locks.

- Emit `thread_start` with `thread`, `daemon`, and `name` before that thread's first other event, and include `parentThread` for workers. Emit `thread_end` with `result` of `terminated` or `uncaught` after that thread's last Java frame and before the launcher counts it as completed. An uncaught record includes the `throwable` ID. A daemon active at process exit may have a trace prefix.
- Emit `monitor` with runtime object identity in `object`, a `phase` of `contended`, `enter`, `exit`, `wait`, or `resume`, and effective recursion `depth`. A resume has a `reason` of `notified`, `timed_out`, or `interrupted` and records the restored depth. Include `method`, with owner, name, descriptor and loader ID, for explicit instructions and implicit method locks. Include the original `pc` for explicit instructions. Emit both through the same instrumentation.
- Emit `class_init_wait` with class, loader, waiting thread, and `ownerThread` for a competing initialization wait. Keep one existing `class_init` start and completion pair attributable to the owner. Publish completion before a waiter proceeds and ensure the trace can demonstrate that order. Keep plugin publication events before a returned handle can be used.

Steps 2–4 can share internal test threads before all launch APIs are available. Gate 4 is ready when every required test passes with the same fixture class files across modes and the Go race detector passes in the generated executables themselves.
