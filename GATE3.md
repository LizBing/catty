# Gate 3 implementation specification

Gate 3 lets a running Catty application admit an external Java 21 JAR and call its classes through the existing interpreter, compiled code, and public method reflection. The acceptance executable must be built before the plugin JAR exists. An already-used compiled call site must dispatch to a late subclass, two loaders must be able to define the same class name independently, and a rejected JAR must leave the running application able to accept and execute a later valid JAR. [Architecture and delivery gates](ARCHITECTURE.md#11-delivery-gates) · [Gate 3 test plan](GATE3-TESTING.md)

## 1. Profile and build contract

Add `catty build --enable-plugins` to select profile `catty-jvm21-gate3` and image ABI `3`. Builds without the flag select `catty-jvm21-gate2` and ABI `2`. The installer recognizes these two exact pairs and validates them before startup or Java execution. The Gate 3 image and build report advertise plugin admission and its limits, alongside the profile-specific bootstrap and opcode inventories. Versions, inventories, and limits derive from one profile definition. Profile selection must affect both build-time admission and runtime installation.

The application image uses the Gate 2 Java subset and engine selection, including `irem` fallback. `--mode aot` forces eligible **image** methods to compile and retains its existing diagnostics for unsupported lowerings. Every concrete plugin method executes in the interpreter under all image modes. Abstract methods carry declarations only. The executable embeds its runtime, verifier, and interpreter. It accepts plugin JARs as data after startup and requires no Java toolchain, Go toolchain, or original application class files at run time.

Keep the Gate 2 Java feature exclusions. Gate 3 admits one single-release, unsigned, classpath JAR per registration. Java-defined loaders, module layers, automatic dependency discovery, resource lookup, service discovery, class unloading, class redefinition, and concurrent loading are outside this profile. The application controls which JARs it runs. The plugin code executes in the same process with access to the supported Java facilities and any application interfaces it can legally invoke.

## 2. Application API

Publish a compile-time API JAR containing stubs for `catty.runtime.Plugins` and `catty.runtime.PluginAdmissionException`. Applications compile against it. On OpenJDK, the test runner substitutes an implementation of the same signatures. In Catty, the bootstrap inventory supplies the declarations and intrinsic implementations. Reserve `catty.runtime` and its descendants in Gate 3. Passing the stub JAR on the Gate 3 image classpath fails the reserved-package check.

| Java method | JVM descriptor | Contract |
| --- | --- | --- |
| `Plugins.readJar(String path) throws IOException` | `(Ljava/lang/String;)[B` | Read a local regular file into a fresh byte array on explicit request from an image application method. Relative paths use the process working directory. Reject nonregular sources, including ones that could block on open, and verify the opened handle before reading. Bound actual bytes read. Raise `IOException` for file and path failures, `SecurityException` for a plugin-defined logical caller, or an admission exception with code `LIMIT` if the file exceeds the compressed-byte cap. A null path raises `NullPointerException`. |
| `Plugins.register(byte[] jar, ClassLoader parent)` | `([BLjava/lang/ClassLoader;)Ljava/lang/ClassLoader;` | Take a private copy of the bytes, admit a new loader, and return its canonical handle. Accept the application loader, a previously published plugin loader in the same runtime, or null for the bootstrap parent. A null array raises `NullPointerException`. A malformed or foreign parent handle raises `IllegalArgumentException`. A candidate rejection throws `PluginAdmissionException` and leaves the parent and other published loaders usable. |
| `PluginAdmissionException.getCode()` | `()Ljava/lang/String;` | Return the stable admission code. The human-readable description is diagnostic text. |
| `Class.getClassLoader()` | `()Ljava/lang/ClassLoader;` | Return the canonical defining loader handle, or null for bootstrap classes and primitives. For arrays, use the defining loader of the component. |
| `Class.forName(String name, boolean initialize, ClassLoader loader)` | `(Ljava/lang/String;ZLjava/lang/ClassLoader;)Ljava/lang/Class;` | Resolve a binary name or Java array name through the supplied loader, for example `ext.Worker`, `[Lext.Worker;` or `[[I`. Null loader means bootstrap. A null name raises `NullPointerException`. An invalid or unavailable name raises `ClassNotFoundException`. A linkage error after a successful name lookup propagates as its Java throwable. Initialize a resolved ordinary class only when requested. Looking up an array leaves its component uninitialized. |

Publish the `Plugins` methods as public and static and `getCode` as public and instance-bound. Make `PluginAdmissionException` a final subclass of `RuntimeException`. Add abstract `ClassLoader`, `ClassNotFoundException` under `ReflectiveOperationException`, `IOException` under `Exception`, and `SecurityException` under `RuntimeException` to the Gate 3 inventory. Give loader mirrors an internal, runtime-owned payload and expose no Java constructor or mutating methods for them. Resolve that payload only from canonical handles of the owning runtime. For `readJar`, check the logical caller past intrinsic and reflection frames so reflection and ordinary calls enforce the same rule. Application code can take paths through ordinary `main(String[])` arguments and read the JAR during Java execution. [Java 21 class lookup and loader APIs](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Class.html)

Use public static factory methods to obtain plugin objects. For example, the application can register the JAR using `Main.class.getClassLoader()`, look up `ext.Worker` with `initialize=false`, invoke its public static `create` through `getMethod` and `Method.invoke`, and cast the result to the application's `api.Base` or `api.Step`. A later registration of byte-identical content yields a fresh loader. An application replaces its own plugin reference by storing the newly returned object.

## 3. Admission transaction

1. **Create a private candidate.** Validate the API arguments and compressed size before copying the array. Snapshot the ancestor chain and use read-only definition metadata during verification, including for ancestor classes whose mirrors have yet to be created. Calculate SHA-256 over the input copy for diagnostics and trace correlation. Sort canonical entry names before class validation to make the first class diagnostic deterministic.
2. **Validate the archive.** Use the Go ZIP reader over the bounded bytes and enforce the limits below. Validate entry names as UTF-8 slash-delimited paths. Reject absolute or drive-prefixed names, backslashes, NULs, dot segments, repeated separators, duplicate names, file/directory conflicts, symlinks, encryption, and unsupported compression. A trailing slash is allowed for a directory entry. Range-check metadata before allocation. Verify actual expanded lengths and CRCs by streaming entries through applicable caps and reading to EOF. Include manifests and non-class entries in the totals. Parse the manifest with case-insensitive attribute names and continuation lines. Reject `Multi-Release: true` or versioned paths, `module-info.class`, nonempty manifest `Class-Path`, `Sealed: true` in main or per-entry attributes, and signature metadata under `META-INF` (`*.SF`, `*.RSA`, `*.DSA`, `*.EC`, `SIG-*`, case-insensitive). ZIP entries stay in memory or are streamed and discarded. The loader performs no extraction or dependency fetch. [Java 21 JAR specification](https://docs.oracle.com/en/java/javase/21/docs/specs/jar/jar.html)
3. **Parse and choose definitions.** Parse every class with the shared version 65.0 reader and enforce structural and profile checks even for a parent-shadowed entry. Match each entry path exactly to `this_class + ".class"`. Reject class definitions in reserved namespaces, classes under `META-INF`, duplicate internal names, and archives with zero class entries. Resolve names parent-first. A structurally valid, profile-compatible definition whose name the parent already provides is shadowed. Exclude it from the candidate definition set and record it in admission evidence. Typed verification and hierarchy checks apply to definitions the loader can actually define.
4. **Verify the effective definitions.** Verify every effective class, including unreferenced ones, through the same typed verifier as image builds. The context sees the candidate's effective class table and the registered ancestor chain. Inspect inherited types and member descriptors from the declaring class's defining loader. Validate superclass and interface kinds, access, final inheritance, hierarchy cycles, required catch and stack-map types, and relevant nest metadata. Before enabling admission, check that the shared verifier enforces live local types at exception edges, uninitialized-object use, protected receiver constraints, and operand and descriptor types before execution. Reject required verification dependencies and unsupported bootstrap facilities during admission. An application member or class symbol may remain unresolved if verification and structural checks succeed without it. Retain method, descriptor, reference kind and original PC for these deferred references. Apply the Gate 2 requirement that declared field and method parameter types needed by preparation are available. [Java 21 class file verification](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.10)
5. **Stage interpreter definitions and validate linking.** Convert effective classes to immutable definitions, with copied retained instructions and symbolic references. Use the same field layout, descriptor and method materialization helpers as image installation. Reject any candidate that fails preparation checks, including cross-loader constraints determinable at preparation. Use detached state for any speculative class layout or constraint checks. Commit the loader's immutable definitions, staged loader-local state, and quota accounting together after validation succeeds. Link or materialize class metadata on demand. Preserve lazy Java symbolic resolution, including sticky Java errors, and run every `<clinit>` only on active use.
6. **Publish or reject.** Assign a loader ID and expose its handle only on success. A failure leaves the registry, loader quotas, parent definitions, parent initiation records, resolution caches, array class cache, Java statics, and existing object state as they were before staging. Creating the returned throwable and recording the rejection trace are ordinary effects of reporting failure. Repeated registration of corrected bytes must succeed even if the failed JAR contained a valid class before the bad one.

### Resource limits

Use inclusive ceilings and test the exact boundary and one unit beyond it. Limit reads to the remaining budget plus one sentinel byte to detect oversized inputs. Reject before allocating or processing data beyond the applicable ceiling. These initial limits are profile constants.

| Limit | Ceiling |
| --- | --- |
| Compressed input | 16 MiB per registration |
| Actual expanded data | 64 MiB per JAR and 4 MiB per entry |
| Central-directory entries and class entries | 4,096 entries and 1,024 class entries per JAR |
| Hierarchy traversal depth | 128 class/interface edges |
| Verification work | 16,777,216 units per JAR |
| Published plugin loaders and admitted class bytes | 64 loaders and 128 MiB of cumulative uncompressed effective class-file bytes per runtime |

Charge verification work before processing class-file table elements, instruction and switch edges, hierarchy visits, handler edges, and frame cells copied or compared. Account for `max_locals` and `max_stack` before allocating frame-analysis storage. Structure traversal so repeated ancestor queries and diamonds consume a bounded budget. Treat metadata sizes as untrusted and enforce aggregate sizes with checked arithmetic. Count all published plugin loaders against the loader limit, including those with entirely shadowed classes. Count effective class bytes only on commit. Apply caps to both `readJar` and direct registration as applicable. Accept stored and deflated entries with the same limits.

### Diagnostics

Use stable admission codes `ARCHIVE`, `LIMIT`, `PACKAGE`, `CLASS_FORMAT`, `PROFILE`, `DEPENDENCY`, and `VERIFY`. Classify ZIP structure, paths, duplicates, CRC and an empty class set under `ARCHIVE`. Classify disallowed JAR features and reserved namespaces under `PACKAGE`, malformed class structure and entry/name mismatch under `CLASS_FORMAT`, and unsupported class versions, features and bootstrap capabilities under `PROFILE`. Use `DEPENDENCY` for a required type the candidate cannot see and `VERIFY` for invalid bytecode, hierarchy or preparation constraints. Preserve these categories through typed errors from the reader and verifier. When available, include the archive entry, internal class name, method and descriptor, original bytecode offset, and the failed limit or feature. Use these same fields in Go errors and diagnostic traces. Catchable Java linkage and initialization failures occur on execution through the ordinary `Outcome` path.

## 4. Loader-aware runtime semantics

- **Lookup and identity.** Give each runtime a bootstrap loader, its application child, and registered plugin children. Keep a separate name-to-definition index per loader. The bootstrap lookup handles its inventory, and delegation precedes local lookup at every other level. A parent never searches children, and siblings see each other only through Java objects passed across an API. If loader A initiates a class defined by loader B, keep B's class pointer, canonical mirror and statics. Preserve application/boot convenience functions for host-facing callers by binding them explicitly to the application or bootstrap loader.
- **Arrays and access.** Intern reference array classes by immediate component `*Class`, which also preserves rank. Use canonical bootstrap types for primitives and primitive arrays. Implement casts, `instanceof`, array allocation and array stores using class identity. Runtime package equality requires the package string and defining loader. Resolve nest hosts using the defining loader and validate mutual membership. Check access to the resolved symbolic owner and member. For protected instance access, use the member's flags and the specified receiver restriction. Qualify default-method traversal by class identity and honor Java overriding and method-selection rules for package-private, inherited, and interface methods. [JVM loading, access and method selection](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html)
- **Symbolic references.** In both `rt/interpreter.go` and `internal/aot/emit.go`, pass the referring method and original constant-pool index for class, field and method operands. Key cached successes and sticky resolution errors by referring runtime class and constant-pool entry, with a typed key for synthetic host operations. Resolve `new`, class literals, casts, `instanceof`, array components, field and method owners, and handler types using the referring class's loader. Resolve handler types against the method that declares the table. Route a failed class literal through Java exception handling at its original PC. Resolve descriptor types in the declaring method's or field's loader, including reflective parameter and return classes. [JVM symbolic resolution](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.3)
- **Loading constraints.** Track initiating loaders and equality constraints for reference leaf types in cross-loader field/method resolution and override preparation. Primitive descriptors impose no cross-loader equality constraint. Compare resolved class identity, including when a constraint becomes relevant on a later lookup. Stage constraint updates and initiation records until the associated operation succeeds. A conflict identified during plugin preparation rejects the candidate. A conflict during execution produces the specified `LinkageError`. With fixed parent-first visibility, related loaders already share any class the parent can see. An absent class in the parent's view must still follow the ordinary resolution and failure timing. [JVM loading constraints and preparation](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.3.4)
- **Invocation and initialization.** Route image and plugin calls through the same `Thread.Call` and `Outcome` paths. Keep receiver checks, resolution, selection and exception transfer consistent for both engines. Track initialization and erroneous state on each defining class. Class lookup with `initialize=false`, public method lookup and array creation leave initializers dormant. Active use calls the existing initialization code, including superclass order, reentry, and failure handling. Reflection uses the caller's access context, selects virtual targets by receiver and preserves the original throwable as the cause of `InvocationTargetException`. A still-live object from an older plugin registration continues using its original class and static state.

### Guarded compiled dispatch

Keep generated virtual and interface call sites on the shared runtime invocation path. For Gate 3 compiled callers, add a single cached successful target per `(caller *Method, original PC, opcode)` in the owning runtime. Perform symbolic resolution and the opcode's required receiver and access checks before consulting the cache. A hit requires the identical resolved declaration and exact receiver `*Class`. On a miss, run the full virtual/interface selection and cache its successful target. Cache entries hold Go-visible pointers. The interpreter and reflection use the same general selector. Final and special calls follow their existing semantics. No assumption about the set of classes in the image may bypass the receiver guard. An admission can add classes without invalidating a successful selection for an existing receiver class. [JVM method selection](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.6)

## 6. Trace and report contract

Extend `CATTY_TRACE` with stable runtime-local numeric loader IDs and parent IDs. Include defining loader IDs on method and throwable records. For dispatch, include the caller and original PC, declaration, target, actual receiver loader, and compiled cache hit or miss where applicable. Preserve the process ID, logical thread ID, depth, bytecode offsets, and throwable IDs used by earlier checks.

Emit one `plugin_admission` event per byte-array registration decision, with `result` (`accepted` or `rejected`), `thread`, and `parentLoaderId` and `jarSHA256` when known. On success include the fresh `loaderId`, `definedClasses`, `shadowedClasses`, `interpretedMethods`, and `deferredReferences` counts. On rejection include `code` and available location fields. Emit a `class_define` event on first materialization with `class`, `loaderId`, and `jarSHA256` for plugin classes. Emit `class_init` on start and completion, including failed completion, with the class and loader IDs. Trace writes must observe the commit boundary. The static build report covers embedded inputs and image engines, and runtime traces supply per-JAR admission and execution evidence.
