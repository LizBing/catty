# ADR-0006: 类库采用三层混合策略

- 状态：Accepted
- 日期：2026-08-22

## Context

java.* 类库是本项目最大的工作量黑洞。单选 clean-room（太慢）、单选派生（许可与耦合问题）都不可行。

## Decision

按类与运行时内核的耦合度分三层：

| 层 | 范围 | 来源 | 纪律 |
|---|---|---|---|
| L1 内核紧耦合类 | String、包装类、集合骨架、Thread/Object、异常层级、引用类 | clean-room 自写 | 主仓 Apache-2.0 |
| L2 机械大体量类 | BigInteger/BigDecimal、regex、java.time 等 | Apache 血统开源移植（Apache Harmony attic；AOSP libcore 需逐文件许可甄别后方可落地） | 每文件 PROVENANCE 登记 |
| L3 符合性 | 行为正确性证明 | jtreg 子集、Harmony 测试套件等 | 放独立 GPL 外部仓（如 catty-conformance），物理隔离，永不进主仓依赖树 |

v1 范围 = "服务端 mini profile"：java.lang 核心 + java.util + io/nio + net + concurrent + time，验收标准为跑通一个 JSON HTTP 微服务。nio/net 大量委托 Go 标准库。

## Alternatives

- 整体 clean-room：工期 +1~2 年，研究阶段不可接受；
- 整体派生 libcore：许可谱系混杂（Harmony 血统 + Google 代码 + OpenJDK 8 移植混存），未审计前整树引入违反 IP 姿态（ADR-0008）。

## Evidence

libcore 自 Android N 起以 OpenJDK 8 库为基础，是 JDK 8 语义最接近的可用开源实现；Harmony 覆盖 Java 5/6 且许可干净。两者互补。

## Consequences

- L1 是学习价值与 IP 价值最高的部分，恰好也是耦合最深必须自写的部分；
- L2 落地前多一道审计工序（登记为 debt 项）；
- PROVENANCE 纪律为产品化预留干净路径。

## Risks

libcore 逐文件许可甄别工作量超预期 → 先移植 Harmony 血统明确的文件，libcore 文件延后。

## Rollback

任一 L2 文件发现许可问题 → 移除并以 clean-room 实现替换；分层结构不受影响。
