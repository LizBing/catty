# ADR-0009: 发射器异常传播机制采用旗标返回（F），panic 方案降为 v2 热点优化

- 状态：Accepted
- 日期：2026-08-23
- 依据：R-0002 异常机制基准（docs/research/R-0002-exception-mechanism.md）
- 关联：ADR-0005（本 ADR 收口其遗留决策）、emitter-abi.md §2

## Context

AOT 发射器必须为每个生成方法选择异常传播机制。ADR-0005 将该决策延后至
有实验证据时收口。两个候选：P=panic/recover（Java throw→Go panic）；
F=旗标返回（方法返回二元组，调用点显式检查）。

## Decision

1. **v1 默认 F**。所有生成方法签名携带 `*kernel.Thrown` 异常通道
   （emitter-abi §2），调用点显式检查转发；
2. **catch/finally 的发射形态**：exc 类型判断链 + 路径复制，不使用
   recover、不做函数拆分；
3. **P 不废弃**：作为 v2 对"已证实热点且方法体无 handler"的内层链路
   优化保留，须经基准证明收益后按方法粒度启用（ADR-0005 隔离层兑现）;
4. **栈深 guard 与机制解耦**：无论 P/F，发射器必须在序言注入深度计量——
   Go 栈溢出是致命 throw 而 Java SOE 可捕获（R-0002 发现③）。

## Alternatives

P 全量启用被否决，三维修据（R-0002）：
- **性能**：P 唯一优势是无 handler 方法的正常路径（~21%），且该优势要求
  "无 defer"纪律；任何 catch/finally/synchronized 方法上 P 反而慢
  （handler 方法慢 2.9×）。临界异常频率 0.6%（浅捕获）/0.06%（逐层重抛）
  远低于服务器负载的典型异常率；f=0.1% 时逐案核算见报告。
- **正确性**：P 的 catch-then-continue 需函数拆分（recover 返回调用者
  而非跳回 catch 后），发射复杂度高且背负误吞 Go runtime panic、跨
  goroutine 漏网即进程崩溃两类语义陷阱。
- **可维护性**：F 的签名污染是机械的、编译期可见的、集中在 ABI 层。

## Evidence

R-0002 三场景中位数（两轮独立运行 ≤3% 偏差，benchstat p=0.000 复验）：
正常路径无 handler P 3.6 vs F 4.6ns；throw-catch 170 vs 2.2ns；
深传播逐层重抛 1595 vs 2.9ns；geomean F −93.4%。全部零分配。
关键限定：P 的正常路径优势严格依赖"只在有 handler 的方法装 defer"
这一发射纪律——纪律一旦破功（无差别 defer+recover），P 全面劣化。

## Consequences

- 生成代码每个调用点多一次 nil 检查（典型负载下总成本可忽略）；
- 发射器不得对 F 方法使用 defer 实现 finally（路径复制代替）；
- 跨 goroutine 异常传播天然安全（flag 是普通返回值）；
- ADR-0005 的调用约定抽象层完成使命后移除（决策已定稿）。

## Risks

- "真实 fixture 方法构成占比未实测"（R-0002 Unknowns）：若热点方法
  几乎全带 handler，v2 的 P 优化空间趋零——不影响 v1 正确性。
- 签名检查遗漏 → 生成代码评审清单 + 机械 lint（实现任务内落地）。

## Rollback

调用约定集中在 emitter-abi 定义的签名模块；切换为 P 只需变更该模块与
catch 发射形态，按方法粒度灰度（ADR-0005 隔离层的最终兑现）。
