# Catty 愿景

- 状态：Accepted（基线 v0.1）
- 日期：2026-08-22
- 来源：初始设计会话；相关决策已固化为 ADR-0002 … ADR-0008
- 变更方式：产品意图变更需新的 ADR

## 一句话定位

> Catty 是一个用 Go 编写的 Java 语言运行时：对象、线程、GC 寄生在 Go 运行时之上，执行引擎以构建期 AOT（字节码 → Go 源码 → 整体编译）为主路径，内置字节码解释器兜底动态特性。

## 问题与机会

1. **冷启动与部署形态**：传统 JVM 冷启动数百毫秒、内存占用高，serverless / CLI / 边缘场景成本高。
2. **现有 AOT 方案的痛点**：GraalVM native-image 的 closed-world 反射配置地狱，以及 SubstrateVM 的复杂度；动态特性失败在构建期而不是降级在运行期。
3. **互操作空白**：Java 业务逻辑与 Go 生态（net/http、crypto、海量库）之间没有低成本的双向桥梁。
4. **研究价值**：同时吃透两个成熟运行时（JVM 语义与 Go runtime 实现），是极少数具备教学与产品双重价值的系统工程题目。

## 卖点排序（宣传与研发优先级一致）

1. 冷启动毫秒级 + 单一静态二进制；
2. 零预热抖动，p99 从第一个请求起稳定；
3. goroutine 底座带来的高并发承载（现代 JDK 上对应虚拟线程叙事）；
4. Java ↔ Go 双向互操作（差异化最强）；
5. 可观测性白嫖：pprof 直接剖析运行中的 Java 线程；`-race` 构建即 Java 数据竞争检测器。

## 目标场景（商业楔子）

serverless 函数 / CLI 工具 / 插件化嵌入（Go 应用嵌入 Java 业务规则）/ 低流量长尾微服务。

## 诚实预期（设计目标，非承诺；一切以 benchmark 证据为准，协议 §26）

| 维度 | OpenJDK (C2 预热后) | GraalVM native-image | Catty 目标 |
|---|---|---|---|
| 冷启动 | 数百 ms | 15–60ms | <10ms |
| 稳态吞吐（热点循环） | 100%（基准） | ~50–80% | v1 达 NI 水平，长期逼近 |
| p99 抖动 | 预热期差 | 好 | 好 |
| 常驻内存 | 高 | 中 | 低 |
| 动态特性 | 全量 | 构建期失败风险 | 解释器兜底：可用但变慢 |

定位清醒：这不是全面超越 HotSpot 的故事，而是"启动 × 尾延迟 × 部署形态 × Go 生态互操作"的组合拳。

## 非目标（v1 明确不做）

- JIT 编译器（自研机器码后端属 v2+ 议题）；
- SecurityManager 及 JVMTI agents；
- Java 商标兼容认证（不做 TCK 声明）；
- 完整 java.* 类库（只做服务端 mini profile，见 architecture.md §8）;
- Valhalla / Loom 特性级对齐（goroutine 底座天然覆盖大部分价值）。

## 项目性质与成功标准

- **性质**：学习/研究起步，保留产品化期权（许可与 IP 姿态见 ADR-0008）。
- **研究阶段成功标准**：M0–M4 里程碑验收链全部通过（见 docs/plans/active/P-0001 与 architecture.md §11）。
- **产品化触发信号**（满足才讨论）：M4 三方对比报告达标；mini profile 类库在真实应用上稳定运行数周；出现明确的外部使用意愿。

## 命名与商标纪律

项目名 Catty。对外叙述使用"Java 语言兼容运行时"，禁止暗示 Oracle/OpenJDK 背书或兼容认证；不将 "Java" 用于产品名主体。
