# Question

Java 引用对象的 Go 表示法，两个候选哪个更优？具体地，在四组微基准（单态调用点、双态/兆态调用点、字段读写、接口断言下行转换）× 继承链深度 3/6 下，ADR-0004 的"具体类型 + 接口混合表示"（方案 A）与"统一 `*Object` + 槽位数组"（方案 B）谁更快、快多少、快在哪一组。

# Context

对象表示法是 AOT 发射器最难回滚的内部决策之一（ADR-0004）。当前 ADR 为 Provisional，置信度 0.65，明确标注"尚无实测证据"、由 P-0002 提供裁决数据。本报告补齐该证据：A（混合）与 B（统一）各自实现一套原型，跑同一份工作负载，回答"混合表示是否值得其实现复杂度"。

# Candidates

- **方案 A（混合）**：Java 类 → Go 结构体，embedding 镜像继承链；引用静态类型不足时提升为 Go interface，走 itab 动态分派；静态类型足够时是直接调用，去虚化由类型系统自然涌现。
- **方案 B（统一）**：一切对象皆 `*Object`（`cls *Class` 头 + 固定槽位数组 `[16]int64`）；每次访问都经类型断言/类标比较分派。
- （第三方案 C：代码生成展开的伪 vtable，P-0002 列为可选。本报告判定其成本高、收益与 A 高度重叠，未实现，见 Unknowns。）

为公平：B 的槽位用**固定数组**而非 slice，使两种表示都只做一次堆分配，从而隔离"访问模式"差异而非分配次数差异。字段槽位 i 对应继承链第 i 层字段。

# Evidence

## 方法

原型为独立 Go module（`docs/research/assets/objmodel/go.mod`，`module objbench`），含 `hybrid`（A）与 `uniform`（B）两个子包，`common` 包保证两候选算术逐位一致。四个基准组 × 深度 3/6，共 12 个基准函数 × 2 候选。工作负载用 `//go:noinline` 构造器 + 跨包非恒定 seed 制造，防止常量折叠与循环不变量外提；对象在基准循环外预分配，循环内零分配。

命令（可复现）：

```sh
cd docs/research/assets/objmodel
go test ./hybrid ./uniform -run '^$' -bench . -benchmem -count=10      # 分配观测
for round in $(seq 1 15); do                                           # 主计时数据（交错）
  for pkg in hybrid uniform; do go test -run '^$' -bench . -benchtime=400ms ./"$pkg"; done
done
go build -gcflags='-m' ./hybrid ./uniform                              # 逃逸分析
```

benchstat 无法安装（无外网访问 `proxy.golang.org`），按计划手工计算中位数/极差。硬件：Apple M1，darwin/arm64，go1.26.5。

## 逃逸分析（`-gcflags=-m`，定性）

- 局部"创建→消费→丢弃"时，**两种表示都把对象留在栈上**（`&D3Leaf{}` 与 `&Object{...}` 均 "does not escape"）。ADR 中"B 阻断逃逸分析"对固定数组设计**不成立**。
- **A 独占**：接口调用在具体类型可证明时被**去虚化+内联**（`devirtualizing a.Compute to *D3Leaf`）。B 无此能力（无具体类型信息可利用）。
- A 的所有 `Compute` 方法均可内联；B 的 `d3LeafCall/d6LeafCall/bi3Dispatch` 可内联，但 **`mega3Dispatch/mega6Dispatch`（8 路 switch）太大无法内联** → B 的兆态分派多一层真实函数调用。
- B 的 `d3LeafCall` 内联后每单态调用多一条 `cls` 加载 + 与类常量比较 + 分支（反汇编证实），A 的直接调用无此开销。

# Findings

区分测量事实与推断：

**测量事实**
1. 四组中 A 从未在稳定方向上显著慢于 B；A 的显著优势集中在**单态调用（~3–5%）**与**兆态调用（~6–11%）**。
2. **字段读写与下行转换两组完全持平**（差异 ≤4%，且方向在深度 3/6 间漂移，属噪声）。固定槽位 `o.f[i]` 与结构体选择器 `l.f_i` 编译为同等的定偏移 load/store。
3. 双态调用接近持平：B 的小型 2 路 switch 被内联为比较链，可与 itab 间接调用打平；该优势仅在 switch 小到可内联时存在。
4. 稳态零分配：两种表示每操作都不产生额外堆分配。

**推断**（由确定性证据支撑，非计时）
5. A 的单态优势来自"无类标检查"（B 每次都要 `cls` 比较）；A 的兆态优势来自 itab 单次间接调用 vs B 不可内联的 8 路 switch + 函数调用。
6. A 独有的去虚化能力（interface 调用在可证明类型处被内联）是混合表示的结构性收益，B 无法获得。
7. 真实 Java 程序中单态调用点占比通常 >90%，兆态集中在框架热点——正是 A 占优的两组，因此 A 的收益面恰好覆盖最常见路径。

# Recommendation

**采用方案 A（混合表示）**。A 在最具代表性路径（单态、兆态）稳定占优，字段与下行持平、零分配；B 无任何稳定优势点（唯一接近的双态仍受噪声淹没，且依赖 switch 可内联这一脆弱条件）。混合表示的实现复杂度因此是"买来的"而非"白付的"。

# Confidence

**0.72**

低于 ADR 自设的 0.8 转正门槛，原因：(a) Apple M1 异构核 + 变频使单样本噪声 ±15–25%，中位稳定度仅 ~±5–7%，无法满足 ±3% 级精度主张；(b) 这是合成微基准，非真实发射器产物；(c) 双态组方向不稳定。但**方向**（A ≥ B，A 在单态/兆态占优）在三轮独立运行 + 确定性汇编证据下高度一致，置信度约 0.9。0.72 是"据此直接转 Accepted"的综合置信度。

# Unknowns

- 双态调用点 itab 与内联 switch 的胜负依赖分支预测器与微架构，未能在本硬件上稳定裁定；真实发射器若为双态热点生成 switch，结论可能变化。
- 固定数组 `[16]int64` 使 B 免于 slice 的二次分配；真实 B 若用变长对象（unsafe 或 slice），字段访问与分配成本会变差，本报告未测。
- 深层 embedding（深度 6 以上）是否触发内联预算耗尽未被覆盖（ADR Risks 所列；深度 6 内 A 方法仍全部内联）。
- 方案 C（伪 vtable 展开）未实现，其与 A 的差异仅定性推断。
- 逃逸分析结论基于手写函数，真实发射器生成的代码形态可能不同。

# 对 ADR-0004 的建议处置

**维持 Provisional + 补实验（方向收敛为方案 A）。**

- 证据**不支持 Superseded**：B 无稳定优势，字段访问的反直觉持平恰恰削弱了 B"槽位访问慢"这一潜在顾虑，但 B 的单态类标检查与兆态不可内联分派是真实且持续的劣势。
- 证据**方向强烈支持 A**，但幅度（3–11%）与合成基准性质使综合置信度 0.72 < 0.8，未达到 ADR 自设的转正门槛。
- 建议 Orchestrator 在 M3 发射器输出真实 AOT 产物后，补一次端到端对照（同一 Java 基准经 A/B 两套调用约定发射），以跨越 0.8 门槛再转 Accepted；同时把 ADR 的 Consequences/Risks 修正为："字段访问非差异点；差异点在单态类标检查与兆态分派可内联性"。
